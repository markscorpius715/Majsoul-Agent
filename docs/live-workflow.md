# Current real-time workflow

## 2026-10-18: Agent owns all input; watchdog instead of takeover (current)

This section overrides the takeover, handback, observer and protector descriptions further down. Those describe `majsoul/live/protection.py`, which is kept in the repository but is no longer used by `run`.

```powershell
& .\.venv-gpu\Scripts\python.exe -u -m majsoul.live run --config configs/live.steam.yaml --execute
```

- **The Agent plays the whole match.** It plays every turn, confirms result screens, and dismisses reviewed popups (away-from-keyboard, connection; `modal_manifest`, at most 3 clicks per popup). It returns to the lobby and stops. Client auto-play is never switched on.
- **Fallback chain:**
  1. the DeepSeek model (`decision.policy: deepseek`);
  2. local efficiency on the same frozen snapshot, at `deadline − decision.local_fallback_seconds`;
  3. tsumogiri, or a recognized PASS, judged only from our own hand area (`emergency`);
  4. the client's own timeout.

  The clock is read once per turn and counted down locally (`operation_clock.py`). With no reading, only `emergency.base_seconds` is assumed. Tsumogiri fires `lead_seconds` before the estimated client deadline, or at `maximum_turn_seconds`, and never clicks after `last_safe_input`. The Agent's decisions end `decision.action_margin_seconds` before that.
- **Watchdog (`watchdog.py`, `watchdog` section):** it never sends game input.
  - A crash, `stall_seconds` of silence, or `startup_seconds` without readiness gets the Agent fenced.
  - A pre-loaded standby (`warm_standby`, loaded `standby_delay_seconds` after the match started) is promoted at once. Otherwise a cold Agent joins the running match. It joins without menus once matchmaking began, so a second match cannot be queued.
  - `restart_limit` restarts per match, with backoff.
  - A closed window ends the run without restarts; a locked desktop delays the restart until it unlocks.
  - `STOP` in the session directory or Ctrl+C stops the Agent and ends the run. The match then continues only on client timeouts.
- **Session files:** `artifacts/live/live-*/`: `watchdog.jsonl`, `watchdog-result.json` (`agent_acceptance` = returned to the lobby with zero restarts), and `agent*/events.jsonl` / `decisions.jsonl`. Triage with `python -m tools.run_triage <run>`.

### 2026-10-18 update after the first full watchdog match

- **Continuous play:** after a match returns to the lobby, a fresh Agent enters the next one through the menus, until `STOP`, Ctrl+C or `watchdog.max_matches` (0 = unlimited). `watchdog-result.json` lists each finished match in `matches`.
- **Time control (`turn_timer.py`):**
  - 7 s base per turn;
  - a 20 s reserve shared by all turns of a hand and restored at the next hand;
  - 5 s turns once the reserve is spent.

  The on-screen reading is the authority. Ordinary turns spend at most `emergency.reserve_per_turn_seconds` of reserve; a riichi tile selection may use the rest.
- **Decisions:**
  - A legal ron/tsumo is always taken (`decision.always_win`).
  - Riichi is one model choice, `riichi:<index>:<tile>`. The Agent clicks the riichi button, then the planned tile once the client highlights the selectable tiles.
  - Our own riichi status comes from our own verified declaration, so an opponent's riichi no longer locks our discards to tsumogiri.
  - An expired selection or an unresolved kan is logged and play continues.
- **Buttons and the fallback step:**
  - A button cut by the edge of the button row is re-read from a padded region, and accepted only if the full button matches a template. This is how the 和 (ron) button is now read.
  - The tsumogiri step clicks a recognized win button, discards the drawn tile on our own turn even with riichi/pass buttons shown, PASSes only in call windows, and never PASSes over a candidate that resembles a win button.

## Single-Request Decision

The main thread handles capture, state tracking, lifecycle, goal recheck, and clicking. An independent daemon worker only runs model I/O, with at most one request and no backlog of waiting requests; input and result snapshots are isolated. Native Jev, DeepSeek, and fallback use cancellable asynchronous interfaces sharing an absolute deadline.

A decision first requests Jev (the current configuration goes through the 7890 proxy); if the first attempt fails and budget remains, the Jev client is rebuilt and retried once, while a direct DeepSeek connection is also started. DeepSeek disables environment proxies and does not inherit HTTP(S)_PROXY or ALL_PROXY. The recovery phase of one decision has at most two parallel model requests; whichever returns a valid result first wins, and the other is cancelled and awaited for exit; stop and state changes also cancel all branches. Both branches share the original deadline, failures do not extend time, and the next decision still prioritizes Jev. The log `timing.attempts` includes backend, attempt number, whether rebuilt, proxy/direct, exception type, and elapsed time.

New process confirmed by the user on 2026-10-10: continuous screenshot recognition → capture one frame with a complete and legal hand, public information, actions, and countdown → freeze the snapshot → asynchronous model decision → recheck own action opportunity → execute the action → verify the hand difference → after success, resume listening. Continuous multi-frame full-table stability is not required. The first snapshot must still pass single-frame state validation, and public UI occlusion follows the existing explicit unknown contract; invisible fields are not zero-filled. Event tracking still independently uses continuous stable frames and does not block the model snapshot.

The request is bound to the current hand epoch, frozen snapshot, own hand and action window, window geometry, and legal action set. While waiting for the model, screenshot recognition continues, but opponent discards, melds, nuki/North extraction, or public glyph animations do not cancel or recompute the already-submitted snapshot. Changes to own hand/buttons, confirmed round change, window geometry change, unknown response buttons, stop, settlement, or deadline arrival still cancel the old request. A late answer after cancellation cannot be executed, and a second decision slot cannot be occupied before the old task truly exits. Failure in the same window or public screen changes do not trigger per-frame re-requests.

A valid answer must still pass recheck against the own hand, action buttons, action legality, click target, window geometry, and deadline in a new screenshot, and no longer waits for full-table stability. `decisions.jsonl` records request_id, frozen observation, legal actions, deadline, and results such as normal choice or cancelled/failed/invalid_action; unexecuted and unverified actions do not count as success.

Discard posterior verification checks the exact hand difference per the user's latest requirement: before execution the target index is indeed the specified tile, and after execution the hand decreases by exactly one tile and only that tile, with no other increases or decreases; automatic sorting is allowed, and red fives are kept separate from normal fives. No proof of new discard pile additions, opponent call attribution, or wall changes is required, nor is full-table stability awaited. A misdiscard is reported as failed; unknown hand, occlusion, no change, or extra increases/decreases remain unknown and follow the protection flow. After success, this operation's budget and request deduplication key are released immediately, returning to listening. The historical strict table-difference tool is retained for analysis of old records; posterior verification for non-normal discards such as pon, kan, and riichi still retains its respective structural proof.

`decision_gate` now includes `blocking_reasons`, `ready_for_model`, current-frame validation issues, snapshot source, event-tracking state frame and stability count, and independently reports button labels/ready. `stable=false` no longer blocks single-frame decisions.
