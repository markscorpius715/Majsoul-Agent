# majsoul Project Rules

Creation date: 2026-09-20. Project goal: Mahjong Soul visual automatic play script for friend-room three-player East-round games.

## Technology and Architecture
- Python; install project dependencies with pip, verify logic with pytest.
- `majsoul/`: screenshots, recognition, state, rules, features, strategy, control, and CLI; `configs/`: layouts and rules; `tests/`: offline tests; `artifacts/`: local screenshots and diagnostics.
- Dependency direction: visual observation → state tracking → legal actions and features → strategy selection → click → re-observe and verify.
- Currently following `GOAL_PROMPT.stability.md` (2026-10-18): the Agent must play whole matches by itself. Do not take direction from the older `GOAL_PROMPT.md` phase plan; keep it only as history. The vision approach is unchanged: fixed ROI + image preprocessing + template/OCR/tile classifier. The old YOLO pipeline is retained only as a historical implementation.
- Phase 5 is only responsible for `GameEvent`s provable from table diffs; Phase 6 only then adds operation buttons, result overlays, decision windows, and RON/TSUMO/GAME_END. `PASS` is an `AgentAction`, not a table event.
- Perception uses a Continual Perception Learning Loop: on first unknown, resynchronize first; only after 3–5 consecutive stable frames remain unknown, deduplicate and generate a HUMAN_REVIEW case; human labels only enter the versioned dataset and training queue, and single-sample immediate training or automatic model release without regression gating is prohibited.
- Jev is the user-specified TypeSafe model. On 2026-09-21 the user confirmed the account has been applied for and explicitly requested implementing the interface in advance; this item overrides the original phase order for decision integration, while visual acceptance must still advance by phase. The protocol is implemented per the official `/v1/systemone` Choice, with DeepSeek fallback supported; account activation does not mean the local key is configured or that real calls have passed. On 2026-10-18 the user dismissed Jev for live play: `configs/live.steam.yaml` uses `decision.policy: deepseek` after Jev failed 4/4 live and `tools/deepseek_ping.py` measured deepseek-flash at decision p95 1.49 s. The Jev adapter is kept, and `policy: auto` restores it.

## Implementation and Verification
- Do not hardcode strategies for specific screenshots, hand patterns, or tests; layouts, detection classes, confidence, and timeouts are all configurable.
- ROI coordinates are saved as x/y independently normalized proportions relative to the reference frame; when the target frame's aspect ratio drift is within the configured threshold, scale separately; when it exceeds the threshold, silently applying them is prohibited, and multiple width-preserving/height-preserving/stretched projection crops must be exported and selected after recognition or human review.
- Four-player replays may be used for cross-mode visual training such as tile faces, glyphs, discards, melds, right-side slots, and general UI; each sample must record its player_count/mode source, and four-player score, North extraction, and event-rule labels must not be mixed into three-player state or rule training.
- Three-player ROI uses the four physical screen slots `bottom/top/left/right`; the legal occupancy combinations are top-bottom-left, top-bottom-right, and left-right-bottom; after stable recognition once at the start, the combination is locked as match-level state, and changing hands only updates seat winds, dealer, and hand number. It is reset only when starting a new match or explicitly resynchronizing, and player numbers must not be fixedly bound to bottom, left, or right.
- The model only selects actions provided by the rule layer; output must be validated; clicking stops when recognition is incomplete, state is uncertain, the window loses focus, or observations are stale.
- (Superseded on 2026-10-18 where it concerns takeover; see the watchdog rule below.) On 2026-10-13 the user updated start acceptance: confirm the hand has started directly from the Agent's current legal observation; if recognition fails, keep retrying, and only take over if it still fails about 30 seconds after recognition begins (`protection.recognition_seconds`). During startup recognition, lightweight UI/clock/animation must not preemptively be judged as failure; operation-deadline monitoring is enabled only after the Agent confirms the hand has started. This item overrides the previous convention of applying 1-second unknown-UI/0.4-second unknown-clock at startup.
- (Superseded on 2026-10-18 by the watchdog rule below; kept as history.) On 2026-10-14 the user approved temporary takeover: recoverable failures are temporarily protected by the client; after the observational Agent resynchronizes, Agent input is granted only during the opponent's turn, after the protection side verifies automatic options are off (discard-after-draw last, tile-sorting preserved) and termination is confirmed; protection is locked to the lobby only when the operator stops, lock screen is confirmed, or the recovery budget is exhausted. The constraints of a single input owner and not starting a new match remain unchanged.
- On 2026-10-18 the user changed operation-clock handling: read the on-screen countdown once per operation window (the first confirmed reading, e.g. 5+20). After that, the Agent counts down locally on a monotonic clock from that frame's capture time (`majsoul/live/operation_clock.py`). Unreadable clock frames later in the same window are not failures. The 0.4-second unknown-clock takeover is removed. If no reading is confirmed in a window, assume only the base time (`emergency.base_seconds`), counted from the earliest point the window could have started. This overrides the earlier unknown-clock rules.
- On 2026-10-18 the user retired the takeover supervisor. The Agent owns all game input for the whole match; client auto-play is never switched on by the system. The Agent's fallback chain is: DeepSeek model → local efficiency on the same snapshot → tsumogiri (discard the drawn tile) or a recognized PASS when our own hand area is clearly recognized (`emergency`) → the client's own timeout. Each step's deadline ends before the next one's. `run --execute` starts `majsoul/live/watchdog.py`, which never sends game input. It only restarts a crashed, stalled or unstartable Agent: it promotes a pre-loaded standby, or starts a cold Agent that joins the running match. Restarts are budgeted; a closed window or the operator's STOP ends the run. The Agent dismisses reviewed in-game popups itself (`modal_manifest`). The old supervisor code (`protection.py`) stays in the repository, unused by the workflow. One input owner remains absolute.
- On 2026-10-18 (after the first full watchdog match) the user decided:
  - **Continuous play:** after a match returns to the lobby, the watchdog starts a fresh Agent that enters the next match through the menus, until STOP/Ctrl+C or `watchdog.max_matches` (0 = unlimited). This overrides "one match per run / never start a new match".
  - **Time control is 7+20 per hand:** 7 s base each turn; a 20 s reserve shared by all turns of a hand and restored at each new hand; once the reserve is spent, 5 s turns. The on-screen reading is the authority (`majsoul/live/turn_timer.py`). Ordinary turns spend at most `emergency.reserve_per_turn_seconds` of reserve; a riichi tile selection may use the rest.
  - **Our own riichi status** comes from our own verified declaration, never from the stick detector. An opponent's unknown riichi must not restrict our discards.
  - **Riichi is one decision:** `riichi:<index>:<tile>` declares and discards together; the tile is clicked after the selection opens, without a second model call.
  - **Wins:** a legal ron/tsumo is always taken (`decision.always_win`). The tsumogiri step clicks a recognized win button and never PASSes over a candidate resembling one. A button cut by the ROI edge is re-read from a padded region.
  - **No quick fatal errors:** an expired riichi selection or an unresolved kan is logged, and play continues.
- Use visible information; do not treat unknown opponent hands as known; record observation blind spots and rule implementation boundaries.
- Do not directly use normal four-player mahjong scores as this project's three-player mahjong scores.
- Verification command: `.venv\Scripts\python -m pytest`; CLI help: `.venv\Scripts\python -m majsoul --help`. You may also activate the virtual environment first and then use `python`.
- Actual integration depends on the window, layout, and valid recognition weights provided by the user; passing offline does not equal completing real-machine verification.
